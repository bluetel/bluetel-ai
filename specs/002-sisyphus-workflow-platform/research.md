# Phase 0 Research: Sisyphus

> **DEPRECATED (2026-08-11):** The Sisyphus workflow platform — including the executor, control plane, admin app, and agent credential pool described in this document — has been deprecated in favour of the Claude Code GitHub Action. This was because the GitHub Action is easier to maintain and configure, and more customizable than the bespoke infrastructure it replaced. This document is retained as a historical design record only; the packages and apps it describes have been removed from the repository.

**Feature**: `specs/002-sisyphus-workflow-platform` | **Date**: 2026-08-05

Each entry records the decision, why it was chosen, and what was rejected. Anything still genuinely open is
listed under [Open spikes](#open-spikes) with the experiment that closes it — none of them block Phase 1
design.

## R1. Multi-turn input to a live agent process (highest risk)

**Decision.** Drive the Claude Code CLI in headless streaming mode with **NDJSON on stdin** as the primary
correction path: `--input-format stream-json --output-format stream-json --verbose`. Keep the process alive
across turns; a correction is an additional user-turn message written to stdin. `--resume` is reserved for
cold-starting from a restored snapshot on a fresh instance, **not** for corrections (FR-044, FR-049).

**Rationale.** This is the only mechanism that satisfies FR-044's "additional user turns on its input stream
process" without ending the session. Restart-per-correction would lose the process's in-memory state and turn
every correction into a snapshot-restore cycle, which is both slower and a larger blast radius.

**Alternatives rejected.**

| Alternative                                         | Why rejected                                                                                                                                                                                                                                                        |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Kill and `--resume` per correction                  | Turns a 2-second correction into a full restore; conversation continuity depends on snapshot integrity every time                                                                                                                                                   |
| Drive the agent via the Messages API directly       | Re-implements the entire coding-agent harness (file tools, bash, permissions) — that is the product we are consuming, not building                                                                                                                                  |
| Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`) | **Not rejected — held as the fallback.** It exposes the same message model more legibly and is the escape hatch if the raw NDJSON shape proves unstable. Held rather than adopted because the CLI is what the POC proved and it avoids re-validating tool behaviour |

**Consequences for the design.** The executor's agent adapter is isolated behind one module boundary
(`agent/` in `sisyphus-executor`) whose public surface is _start / send-turn / pause / snapshot / stop_. Both
the CLI-stdin implementation and the SDK fallback satisfy it, so switching is a swap of one module rather than
a rewrite. **This boundary is load-bearing and must exist before the spike concludes.**

**Known constraint.** `--output-format stream-json` requires `--verbose`. The NDJSON input shape is documented
only at the flag level, which is why S1 exists.

## R2. Session persistence and the path-pinning trap

**Decision.** Pin the workspace root to a **fixed absolute path** (`/workspace`), set `CLAUDE_CONFIG_DIR` to a
directory **inside** that root, and assign the session identifier ourselves via `--session-id` with a UUID
generated by the control plane.

**Rationale.** The agent stores conversation state in a directory derived from the absolute working directory
(slashes replaced by dashes). A snapshot restored onto an instance that checked out to a different path leaves
`--resume` unable to find the session. Pinning the path makes the mangled directory name identical on every
instance; relocating the config dir inside the workspace makes the whole state tree a **single tar target**
(FR-051). Assigning the identifier removes the need to parse it out of agent output, so a workflow is
addressable even if the run dies before producing any (FR-052).

**Alternatives rejected.**

- _Parse the session id from result JSON_ — nothing to parse if the run fails during bootstrap.
- _Symlink the config dir_ — tar-following-symlinks behaviour differs by flag and platform; a real directory
  inside the workspace has no such ambiguity.
- _Rewrite the mangled directory name on restore_ — depends on an undocumented naming scheme; pinning the path
  makes it moot.

**Snapshot contents.** One `tar.zst` per snapshot containing the whole workspace root: every repository
checkout (working tree **and** `.git`, so uncommitted work and index state survive), plus the relocated agent
config tree. Conversation state alone is insufficient — restoring history onto a clean checkout desynchronises
the model's beliefs about the filesystem from reality (FR-050).

**Truncated-tail handling.** The conversation log is append-only and **not** written atomically, so a crash can
leave a partial final line. Restore parses line-by-line, discards a trailing line that does not parse, and
records that truncation occurred (FR-053). This is a normal path, not an error path.

## R3. Pause, interruption and stop are one code path

**Decision.** A single `suspend(reason)` routine implements pause, spot-interruption warning, and stop-for-later:
quiesce the agent at a turn boundary → snapshot → register the snapshot → park as resumable → release compute.
The three differ only in the `reason` recorded and whether compute is released immediately.

**Rationale.** FR-054 requires it, and the reasoning is practical: interruption handling that is only exercised
when a spot reclamation happens is handling that is never tested. Routing the user-facing pause button through
the same code makes it exercised on every manual pause.

**Alternative rejected.** Separate interruption handler — the failure mode is that it rots, and it rots
silently until the first reclamation of a long run.

## R4. Shared contract package — three consumption modes from one definition

**Decision.** `packages/sisyphus-api` owns the schema, the tRPC router and its resolvers, consumed three ways
from one definition:

| Consumer                 | Mode                  | Mechanism                                                           |
| ------------------------ | --------------------- | ------------------------------------------------------------------- |
| `sisyphus-admin`         | Server implementation | Route handler mounts the router                                     |
| `sisyphus-control-plane` | In-process caller     | `createCallerFactory` — no network hop, no HTTP, no auth round trip |
| `sisyphus-executor`      | Typed remote client   | Imports `AppRouter` **type only**; `createTRPCClient` over HTTP     |

**Rationale.** FR-006 requires all three modes from one definition — a compile-time-checked executor client
that imports the types rather than restating them, and a control plane that calls in-process rather than over
the network — while FR-005 makes this package the single place the schema and API surface live. tRPC's
server-side caller gives the
control plane direct invocation with the same validation and the same resolvers, so there is exactly one
implementation of every operation. The executor imports only the router _type_, so no resolver code — and no
database driver — is reachable from the instance.

**Established patterns adopted.** A `createTRPCSetup()` factory returning `{ t, createTRPCContext,
createCallerFactory, createTRPCRouter, publicProcedure }`, with `superjson` as the transformer and an
`errorFormatter` that flattens `ZodError` into `data.zodError` so the panel can render field-level validation.
Client side: `httpBatchStreamLink` + `loggerLink` (dev only, plus downstream errors), an `x-trpc-source` header
per caller, and a single `QueryClient` singleton in the browser with a fresh one per server render. RSC reads go
through hydration helpers that wrap context creation in React `cache` and tag requests `x-trpc-source: rsc`.
`RouterInputs`/`RouterOutputs` are exported as the only sanctioned way to type anything API-derived — a
hand-written DTO mirroring a procedure is the "restating them" FR-006 rules out.

**Three adaptations the established shape needs for this feature.**

1. **The additional-context hook must be async.** The pattern's hook is synchronous, which is sufficient when
   context is just `{ headers }`. Sisyphus resolves a session **and** a permitted-profile set, both of which
   require awaits, and FR-190 requires that resolution to happen once per request rather than per resolver.
   `fetchRequestHandler` and `createCallerFactory` both accept a promise-returning context creator, so this
   costs nothing structurally — but it has to be built in from the start, because the synchronous version
   forces scope re-derivation into every resolver, which is the silent-leak shape FR-190 cannot tolerate.
   The scope is exposed as a **memoised resolver**, not a resolved array, so health checks and the executor's
   high-frequency machine calls never pay for a grants query.
2. **No root package export.** Four subpaths (`./server`, `./client`, `./contracts`, `./db`) instead of one root
   barrel. The FR-005 surface split and the executor's types-only guarantee then hold by module resolution
   rather than by reviewer attention; with a root barrel, `postgres` and every resolver are one import away from
   a panel client component.
3. **Input schemas live in the package, not inline in resolvers.** Exported from `./client` and consumed by both
   the resolver's `.input()` and the panel's form resolver, so the two cannot drift. This is what makes the
   flattened `data.zodError` actually useful — field-level rendering requires the client to know the same field
   names the server validated (FR-008).

**Alternatives rejected.**

- _REST + OpenAPI codegen_ — FR-006 requires the executor to import the types rather than restate them, which
  rules out a generated client; also two artifacts to keep in sync.
- _Executor imports the router value_ — pulls resolvers and the DB driver onto the instance, breaking the
  FR-005 surface split and widening the blast radius of a compromised bundle.
- _GraphQL_ — no benefit here; the panel is the only consumer needing shaped reads.

**The authorisation consequence is architectural, not cosmetic.** FR-190 says a workflow outside the
requester's scope must not be disclosed _including its existence_ — counts and aggregates must not leak it.
That cannot be a per-resolver `if`. It goes in the **context**: the context resolves the caller's visible
execution-profile ID set once, and every workflow query is built from a scoped base selector that already
carries the predicate. Retrofitting this later means auditing every resolver, which is why it is a Phase 1
design output rather than an implementation detail.

## R5. Database and ORM

**Decision.** PostgreSQL (RDS, one instance per stage) with **Drizzle ORM**, schema and forward-only migrations
owned by `sisyphus-api`. Deploy fails closed on an unmigrated database (FR-010).

**Rationale.** The workload is relational and heavily join-shaped — workflow → iterations → external actions →
per-entry results — and the access-scoping model in R4 wants composable query builders rather than a document
store. Drizzle's schema-as-TypeScript keeps the entity definitions and their inferred types in the same package
that owns the contract, so a schema change that breaks a resolver breaks `typecheck` rather than production.

**Alternatives rejected.**

- _Prisma_ — a separate schema language plus a generate step; the generated client also complicates the
  executor's "types only, no driver" constraint.
- _DynamoDB_ — the filtering in FR-013 (compose user × status × workspace × repository × profile) is exactly
  what a relational engine is for and exactly what single-table design makes painful.
- _Aurora Serverless v2_ — worth revisiting on cost, but cold-start latency on the panel's read path is a
  worse first-day trade than a small provisioned instance.

**Log and snapshot storage.** S3, private and encrypted, partitioned per workflow, with a lifecycle policy per
object class (FR-071). Postgres holds pointers, never payloads.

## R6. Streaming live output to the panel

**Decision.** The executor writes sanitised log segments to S3 continuously **and** reports them to the machine
surface. The panel subscribes over **SSE**, backed by Postgres `LISTEN/NOTIFY` fan-out. Archived reads are
served from S3.

**Rationale.** FR-046 requires both halves — durable capture independent of the panel being reachable, and
near-real-time visibility (SC-002) — while FR-047 requires the buffering that makes each survive an unreachable
API. SSE is one-directional (which is all the log needs), survives the CDN in front of the site, and needs no
second protocol. Supervision actions travel as ordinary mutations, not over the stream.

**Alternatives rejected.**

- _WebSockets_ — bidirectional capability we do not need, plus connection-state handling at the CDN edge.
- _Polling_ — the existing POC polls; it is the reason live output feels laggy and it scales badly against
  SC-002.
- _tRPC subscriptions over WS_ — couples the log transport to the RPC layer for no gain.

**The unresolved risk: `LISTEN/NOTIFY` needs a session, and Lambda wants a pool.** `LISTEN/NOTIFY` only works on a
**pinned session connection**. A Lambda-backed panel behind RDS Proxy or pgbouncer in _transaction_ mode does not
have one — the listener would be silently reassigned between statements and simply never receive notifications.
Compounding it, Lambda response streaming through CloudFront has its own duration and buffering limits, and an SSE
stream that buffers is not a live log. R1 and R2 carry comparable risk and both got spikes; this carries SC-002
and had none, which is why **S3** now exists.

The fallback if S3 fails is not a redesign: keep SSE as the client contract and change what fans out behind it —
short-poll `log_segments` by `(workflow_id, sequence)` from within the SSE handler, or move the stream endpoint off
Lambda onto a small always-on process holding a direct connection. Both preserve the panel-side contract and the
sequence-based reconciliation, so the choice stays a transport decision rather than a rewrite. Session-mode pooling
is the third option and is listed last deliberately — it trades the pool's whole benefit for one feature.

**Cache freshness beside a live pane.** The shared `QueryClient` sets a 30-second default `staleTime`, which is
right for configuration reads and wrong next to an SSE log. Live-surface queries — workflow detail, the state
chip, the needs-attention count — set a shorter `staleTime` explicitly and are invalidated by the same
`LISTEN/NOTIFY` events that drive the stream, so a state chip cannot sit on a stale value while the log beside it
advances. Decided here rather than discovered in review, because the default is invisible at the call site.

**Ordering.** Every segment carries a monotonic sequence number scoped to the workflow. Segments concatenate
across resumptions into one continuous log (FR-046), so the panel reconciles by sequence, never by arrival
time.

## R7. Compute provisioning and cost attribution

**Decision.** EC2 via the AWS SDK from the control plane. Instance type and capacity mode come from the
execution profile. Interruptible (spot) is the default with on-demand available. Bootstrap via user-data that
installs and starts the executor. Every instance is tagged with its workflow ID (FR-039, FR-041).

**Rationale.** The job spec must control size and price (FR-036), which rules out a fixed-shape runtime.

**Alternatives rejected.**

| Alternative | Why rejected                                                                                   |
| ----------- | ---------------------------------------------------------------------------------------------- |
| Fargate     | No spot-with-warning semantics comparable to EC2's 2-minute notice, which R3 depends on        |
| Lambda      | 15-minute ceiling; a coding run is routinely longer                                            |
| A warm pool | Contradicts the per-run isolation in FR-042 and complicates credential hygiene between clients |

**Interruption notice.** The executor polls instance metadata for the reclamation warning and calls the R3
`suspend()` path on receipt. Polling rather than an event subscription keeps the detection inside the process
that owns the snapshot.

**Leak prevention.** A reconciliation sweep (FR-039) compares tagged instances against non-terminal
workflows in both directions: an instance with no live workflow is terminated; a workflow whose instance has
vanished or whose heartbeat lapsed is moved to resumable or failed with the reason recorded.

## R8. Integration packages and scheduling

**Decision.** One standalone package per integration type — `packages/sisyphus-integration-jira` is the only
one in scope (FR-095, FR-192). Each implements a connector contract owned by `sisyphus-api`:

```
discover(config, since) → CandidateItem[]     // query the external system
resolveProfile(item, mappings) → profileId    // ordered first-match (FR-130)
assemblePromptParts(item) → PromptParts       // title, url, body, comments (FR-159)
writeBack(item, event) → ExternalActionResult  // pickup / skip / outcome comments
validate(config) → ValidationResult            // connectivity check before enable
```

**Rationale.** The user's requirement is a standalone package per integration; the contract makes that
structural rather than conventional. `sisyphus-api` owns the interface (so the control plane depends on the
abstraction, not on Jira), and no integration package imports another.

**Scheduling.** EventBridge Scheduler, one schedule per enabled integration, created/updated/removed by the
control plane whenever schedule or enabled state changes (FR-100). Each tick invokes the control plane.

**Alternatives rejected.**

- _One `sisyphus-integrations` package with a subdirectory per type_ — the user asked for standalone packages,
  and it also lets one connector's dependencies leak into another's install graph.
- _A single cron sweeping all integrations_ — one slow or hanging connector starves every other board, and
  per-integration coalescing (FR-103) becomes bookkeeping instead of a scheduler property.
- _Webhooks_ — explicitly out of scope; polling is self-healing after missed ticks because matching is
  evaluated against current label state.

**Exactly-once claiming.** A `ticket_claim` table with a unique constraint on `(integration_id, external_id)`,
written in the same transaction that creates the workflow. The unique index — not application logic — is what
makes FR-102 hold across restarts and overlapping ticks. Claims live in our database, never in the tracker.

## R9. Authentication

**Decision.** Google OAuth via Auth.js, restricted by `hd` (hosted-domain) claim **verified server-side** against
an allowlist. Users are auto-provisioned on first sign-in with the `engineer` role (FR-170). Sessions are
database-backed so deactivation and role revocation take effect on the next request (FR-175).

**Rationale.** FR-175's "next request, not next sign-in" requirement rules out self-contained JWT sessions —
a stateless token cannot be revoked mid-life. A database session lookup per request is the mechanism that makes
revocation immediate.

**Executor credentials.** Short-lived JWTs minted by the control plane, scoped to one workflow and to the
machine surface only, carrying `workflow_id`, `profile_id` and an audience claim (FR-037). The machine surface
verifies the audience and matches `workflow_id` against the target of every write (FR-018). Renewal is
a machine-surface operation the executor calls before expiry.

## R10. Output sanitisation and redaction

**Decision.** A two-stage pipeline in the executor, applied to agent output **and** `setup.sh` output
(FR-045, FR-089): strip ANSI/VT control sequences, spinner frames, cursor movement and carriage-return
redraws; then redact secrets by pattern plus known-value matching against every credential the bundle installed.

**Rationale.** Known-value matching is what catches a client credential in an unrecognised format — pattern
matching alone only catches the shapes we anticipated. Both stages run **before** anything is persisted or
transmitted, so an unsanitised copy never exists at rest.

**Reference behaviour worth keeping from the POC** (reimplemented per FR-002, not imported): control-sequence
stripping, process-group spawn with SIGKILL to the whole group on timeout, and pushed-commit verification
against the pre-execution remote SHA.

## R11. Design system and design-lint

**Decision.** `apps/sisyphus-admin/DESIGN.md` conforming to the DESIGN.md alpha spec — front matter
(`colors`, `typography`, `spacing`, `rounded`, `components`) plus exactly eight `##` sections in the mandated
order. Tokens are the instrumentation system in FR-023. Enforced by a cached `design-lint` Nx target with the
linter as a **pinned devDependency of the app** — never `npx`, which resolves outside the lockfile and is
invisible to the affected graph.

```json
"design-lint": {
  "executor": "nx:run-commands",
  "options": { "command": "design.md lint DESIGN.md", "cwd": "apps/sisyphus-admin" },
  "cache": true,
  "inputs": ["{projectRoot}/DESIGN.md"]
}
```

**Precedence.** `DESIGN.md` → theme tokens (`globals.css`) → components. The document wins; the code gets
corrected (FR-021). Literal colours, font sizes, spacing or radii in a component are defects (FR-021).

**Component layer.** shadcn-style primitives with variants via `cva`, class composition through a single shared
`cn` utility (`clsx` + `tailwind-merge`) so overrides resolve predictably (FR-033). Tailwind is pinned
at v3 workspace-wide, so the token layer is CSS variables consumed through the Tailwind theme rather than v4
`@theme`.

**Known design-lint findings and their dispositions** (FR-022's "zero errors, explained warnings"):

| Finding                                                   | Disposition                                                                        |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Contrast error on a component's text/background           | Real WCAG AA failure — fix the token, never relax the check                        |
| Unknown component property (`borderColor`, `borderWidth`) | Accepted with a warning by the spec — explain in the Components prose              |
| `orphaned-tokens` on theme variants (dark-mode pairs)     | Inherent to expressing two themes in a flat token map — explain once; not a defect |
| Missing-section warning                                   | Add the section, or declare it in `omitted:` with a reason                         |

## R12. Infrastructure and CI

**Decision.** SST v3 (Pulumi) with `packages/sisyphus-infra` providing the reusable constructs and each
deployable composing them. Environment values come from Parameter Store at deploy time; secrets are wrapped so
they are not stored in plain text in state. Separate **bootstrap** and **application** stages per environment.
CI is the workspace's **existing GitHub Actions pipeline**, extended with OIDC federation — no long-lived
access keys (FR-068, FR-069).

**Established patterns adopted.**

- `getResourceIdentifier(name)` → `{project}-{stack}-{name}` for every resource, so stages are isolated inside
  one account by naming.
- `getPlainStage(sstStage)` strips known suffixes (`-bootstrap`, `-website`) so a stage name maps to its
  environment.
- `getEnvSecret(secrets, key)` wraps values in a Pulumi secret by default, with an explicit opt-out for the
  bootstrap-time values that cannot be secrets (they are needed to deploy at all).
- A `trigger-deploy` Nx target per deployable so the pipeline deploys only affected projects.
- **Create-once, look-up-everywhere** for the CI identity provider: the production bootstrap creates it; every
  other stage looks it up and **throws a message naming the bootstrap step** if absent. This is the pattern
  that turns a confusing raw AWS "not found" into an actionable error.

**What already exists, and is therefore extended rather than rebuilt.** `.github/workflows/ci.yml` already
runs the two jobs the constitution names — a `qlty` code-health job against the PR base ref, and a `main` job
running `nx affected -t lint test typecheck` — resolves Node via `node-version-file: .nvmrc`, discovers deploy
targets with `nx show projects --affected --withTarget=trigger-deploy`, gates deployment to `main` and
`staging`, and raises a per-app approval issue recording app, stage and commit. `.github/workflows/deploy.yml`
fires on an `/approve` comment from a user with write permission, already declares `id-token: write`, and runs
`nx run <app>:deploy --configuration=<stage>`. So FR-067, FR-069 and FR-070 are largely **already satisfied by
the repository**; what Sisyphus adds is `design-lint` to the affected target list, the OIDC trust relationship,
and a `trigger-deploy` plus `deploy` target per deployable (no project declares either today).

**The federation shape.** GitHub Actions' OIDC issuer is `https://token.actions.githubusercontent.com` with a
`sub` of the form `repo:<org>/<repo>:ref:refs/heads/<branch>`. Branch restriction is therefore expressible in
the **trust policy itself** — the production role trusts only `refs/heads/main`, staging only
`refs/heads/staging` — so FR-067's "protected branches only" rule is enforced by IAM rather than by pipeline
configuration alone. The pipeline's own branch conditions remain as defence in depth.

**Alternatives rejected.** **CircleCI** — an earlier draft of this research chose it, and it is rejected: it
would stand up a second CI provider beside a pipeline that already implements both blocking gates and the
approval flow, leaving one of the two systems not running `design-lint`, and its OIDC subject
(`org/<ORG_ID>/project/<PROJECT_ID>/user/<USER_ID>`) carries **no branch component**, so branch gating could
not live in the trust policy at all — strictly weaker than what GitHub Actions gives for free. Long-lived IAM
keys in CI configuration (FR-068 forbids it, and it is the single worst credential to leak); a self-hosted
runner with an instance role (more infrastructure to own than the problem warrants).

**Deploy approval.** Deploys run only from `main` (production) and `staging` (staging), only for affected
projects with a `trigger-deploy` target, and require an explicit approval recording who approved which commit
for which stage (FR-067, FR-070).

## R13. Notifications

**Decision.** Slack Bot API `chat.postMessage` to a DM channel opened with `conversations.open`, using the
existing Bluetel Slack app's bot token from the secret store. Recipients are resolved from Google identity to
Slack user ID by email lookup, cached with the user record. Slack DM is the only channel (FR-136).

**Rationale.** The app already exists and can DM staff directly, which is the requirement. Email lookup is the
only reliable join between the two identity systems.

**Failure isolation.** Delivery runs **outside** the workflow's state transition. A notification row records
every attempt with its outcome; failure is recorded and surfaced but never alters workflow state (FR-141,
SC-042). An unresolvable Slack identity marks the user unnotifiable and is surfaced in the panel.

**Coalescing.** A short debounce window per workflow collapses rapid transitions, and an integration tick that
starts many workflows emits one summary rather than N messages (FR-139).

## R14. Multi-repository workspace mechanics

**Decision.** Independent `git clone` per workspace entry into `/workspace/<subdirectory>`, all beneath the
pinned root. Entry subdirectories are validated at profile-enable time for uniqueness and for resolving inside
the root (FR-111). Checkout is fully sequenced **before** the agent starts; any entry failing fails the
workflow naming that entry (FR-112).

**Rationale.** The agent's working directory is the root, so it can read across entries in one session — the
whole point of US10. Independent checkouts keep each repository's history intact and keep the snapshot a single
tar of the root.

**Alternatives rejected.** Submodules or subtrees (couples the repositories in ways the clients did not ask
for, and rewrites their history model); a monorepo-style single checkout (not what the repositories are).

**Cross-repository PRs.** One branch name, derived from the primary entry's skills, used across every changed
entry; each PR body cross-references the others (FR-116). Merge order is skill-defined (FR-117) — Sisyphus
records per-entry results and never decides sequencing.

**No atomicity claim.** Cross-repository changes are not atomic at the version-control level and the spec says
so. Partial-landing is a first-class recorded outcome (FR-118), not an error to be papered over.

## R15. Model identifiers

**Decision.** The execution profile's `model` field is constrained to a small allowlist of exact model
identifiers, stored as an enum in `sisyphus-api`: `claude-opus-5` (default), `claude-sonnet-5`,
`claude-haiku-4-5`, `claude-fable-5`.

**Rationale.** Free-text model strings become 404s at run time, on a paid instance, after bootstrap has already
completed. An enum makes an invalid model a validation error at profile-enable time. IDs are used exactly as
written, with no date suffixes appended.

**Consequence.** Adding a model is a migration plus an enum change in one package — deliberately a reviewed
change, since model choice drives both cost and capability.

## R16. Infrastructure authoring shape and the config-file split

_Added 2026-08-06. Supersedes the provider-injection approach the first implementation took; R12's naming,
stage and secret patterns are unchanged and still apply._

**Decision.** A primitive in `sisyphus-infra` is a plain arrow function `createX(config)` that instantiates
`sst.aws.*` / `aws.*` resources directly and returns a named object of what it created. No provider interface,
no injected constructor, no structural redeclaration of the deployment tool's own types. Composition happens
by passing **created resource handles** between primitives; a resource needing an identifier that exists only
after a later resource is built gets its own exported `attachX` function called at the end of `run()`. Each
deployable carries three config files — application, bootstrap, install — and the typecheck target filters
generated code rather than excluding it.

**Rationale.** The injection layer existed for one reason: to let the package typecheck and unit-test without
`sst install`, since the ambient `$config` / `sst.*` globals are declared only by the generated
`.sst/platform/config.d.ts`. The no-op **install config** removes that constraint — it declares the providers
with no env dependency and an empty `run()`, so type generation succeeds on a fresh clone with no credentials
and can run from `postinstall`. The **loose-check filter** removes the second half, absorbing the generated
tree's non-strict errors without weakening the gate elsewhere. With both in place, the injection layer buys
nothing and costs a set of types that exist only to be satisfied, plus tests that assert a fake was called.

**Why the tests go with it, and what replaces them.** Testing `createBuckets` through a Pulumi mock asserts
that the constructor we called is the constructor we called: it restates the implementation, breaks on rename,
and catches no defect a deploy would not. What is worth asserting is separated into pure modules and kept
under test — `getResourceIdentifier`, `getPlainStage`, retention days and transitions per object class, the
content of each policy document, and the exact trusted subject the CI identity provider will accept. A mistake
in those is a security or retention defect that no deploy will report.

**Why three config files.** Their `app()` preconditions differ and are mutually unsatisfiable. The application
config validates a dozen values before it can name the app. The bootstrap config must run when no stack and no
parameters exist, reading a minimal schema from the parameter store over the ambient credential chain. The
install config must run during `pnpm install` on a fresh clone, where neither of the others could complete.
One file with a stage-suffix branch makes every invocation evaluate the other two's preconditions. Every
command acting on a stack — deploy, destroy, unlock — names its config file; a `destroy` that omits it loads
the wrong configuration and mis-plans the teardown. The install config's provider versions must be pinned to
exactly what the application config declares, or the generated types describe something a deploy will not
resolve.

**Two mechanics that look stylistic and are not.** Every import inside a config file is a dynamic
`await import()`, and configuration is read inside `app()` / `run()` rather than at module scope. The ambient
globals do not exist at module-evaluation time, and `createSafeEnv` snapshots `SKIP_ENV_VALIDATION` when its
module is first evaluated — a static import reads it before the config has set the stage. Separately, a
Pulumi-wrapped secret cannot be passed to a provider constructor argument needed to _build_ that provider;
that one call site takes the value unwrapped and says why.

**Alternatives rejected.** Keeping provider injection (the layer the constraint that justified it no longer
exists to justify). Excluding `.sst/**` from `include` (the globals stop resolving and the config files fail
to compile — the gate would pass by no longer checking the code that matters). Deleting the pure layer along
with the construct tests (loses the assertions on retention and the OIDC trust claim, which are the only
infrastructure mistakes that fail silently).

## R17. The panel's application shell

_Added 2026-08-06._

**Decision.** One `(app)` route group whose `layout.tsx` renders the shell — persistent left sidebar plus top
bar — wrapping every authenticated screen. `sign-in` sits outside the group. `not-found.tsx` and `error.tsx`
live at the route root. `/` is a redirect, not a screen.

**Rationale.** The shell must be structural rather than a component each screen remembers to import, because
the failure mode of the latter has already happened: twelve screens shipped reachable only by typing a URL.
A route group makes inclusion the default and omission the deliberate act. `sign-in` is outside because it is
the one screen a signed-out visitor may render, and the shell has nothing to show them. The boundaries sit at
the root so they also catch the `notFound()` thrown by the admin authorisation check, which currently lands on
the framework's unstyled default.

**Role filtering, not hiding.** The admin section is filtered out of the sidebar by session role rather than
hidden with CSS, so the nav never advertises a surface that will answer `NOT_FOUND`. This keeps the shell
consistent with FR-190, which treats the _existence_ of an out-of-scope resource as the thing not to disclose.

**Alternatives rejected.** A shared `<Shell>` component imported per screen (same omission failure, one import
away). A dashboard at `/` (a thirteenth screen with no requirement behind it, and a second place for the
workflow list's queries to drift from). Rendering admin links disabled rather than absent (discloses that the
surface exists).

**Outcome, 2026-08-07.** Built as described, and the route-group choice proved load-bearing in a way the
decision above understated: a boundary renders inside the layout chain of the segment it catches, so a root-only
`not-found.tsx` renders the non-admin's refusal as a bare card outside the shell. **Four** boundary files were
needed, not two — one pair inside `(app)` for refusals thrown by screens, one pair at the root for unmatched
URLs and for the refusal the shell layout itself throws, since a boundary cannot render inside the layout that
threw.

## R18. Where the notification path lives

_Added 2026-08-07, decided during implementation._

**Decision.** Delivery — Slack messenger, recipient selection, coalescing planner, the audit row — lives in a
shared package, `packages/sisyphus-notify`. Both emitters depend on it and neither depends on the other: the
control plane composes it in its own composition root, and `sisyphus-api` declares a one-method port
(`WorkflowEventEmitter`) that its host injects.

**Rationale.** The nine FR-136 events are written from two places and only two: the control plane's reconcile
sweep sets `failed` and `parked_resumable`, and `sisyphus-api`'s `reportTerminal` sets the other four terminal
outcomes plus `review_iteration_failed`. Nothing else in the system writes a terminal state — established by
grep, not assumption. So the delivery layer has exactly two callers in different packages, which is what a
shared package is for.

The port on the `sisyphus-api` side is what keeps the dependency arrow honest: that package must not know how a
notification is delivered, who receives it, or that Slack exists. It knows only that something may want to be
told. When the port is absent the emission is a silent no-op, which is the correct default — FR-140 requires
that an unnotifiable recipient never fails the run that triggered the notification.

**One non-obvious fact this turned on.** The machine surface is mounted by the **panel**
(`apps/sisyphus-admin/src/app/api/machine/[trpc]/route.ts`), not by the control plane. Five of the nine events
therefore originate in a request served by the network-facing deployable, which is why the panel — not the
control plane — is where the notifier gets injected.

**Alternatives rejected.** Adding an `exports` field to the control-plane app and depending on it from the panel
(an app depending on another app; it would also have made the panel's build pull in the provisioning code that
FR-035 exists to keep separate). Emitting inside the state transaction (a throwing notifier would roll back the
outcome even with the throw swallowed — so emission happens after commit, and the transaction is a separate
named function specifically so an emission cannot be added inside it). Emitting on every report rather than
only when the write was recorded (FR-047 retries would announce twice).

## R19. What the assembly gate can and cannot assert

_Added 2026-08-07, decided during implementation._

**Decision.** The gate (SC-063) asserts the **module-level** condition — no shipped file without a production
caller — via `knip --production`, run in CI outside the `nx affected` set. It does not attempt the symbol-level
condition.

**Rationale.** Module-level is SC-063's actual wording, and it catches the failures that occurred: it detects a
planted orphan, detects a module whose only production caller is removed while its barrel export and its tests
remain, and on its first genuine run found thirteen orphaned files across two complete features. Running it
outside `nx affected` is deliberate — knip is not nx-aware, and the caller that went missing usually lives in a
project the diff never touched.

**Why not symbol-level.** Measured, not assumed. `--include-entry-exports` reports the entire `sisyphus-infra`
public API as dead, because every deployment config imports it as
`const { createBuckets } = await import('@bluetel-ai/sisyphus-infra')` and knip does not attribute names
destructured from a dynamic import — the module resolves, the symbols do not. Independently, production mode
reports ~2,060 exports used only by tests. Gating either would mean thousands of ignore entries, which is the
silent-suppression failure the gate exists to prevent. Structurally the module-level check absorbs much of the
residue anyway: barrels are deliberately not production entries, so a module reachable only through one falls
out of the graph and is reported.

**The trap worth recording.** `knip --production` only honours entry and project patterns carrying a trailing
`!`. No pattern in this repository had one, so the production run resolved an empty entry set, analysed **zero
files**, and exited clean — for as long as it had existed. A gate that passes instantly and reports nothing is
the shape of this failure; both `knip.json` and the CI step now carry a comment saying so.

## Open spikes

Neither blocks Phase 1 design; both must close before the code they gate is written.

### S1. NDJSON stdin turn injection (gates US2)

**Question.** What exactly does a user-turn message on `--input-format stream-json` stdin look like, and does
injecting one mid-request deliver guidance to the in-flight request (FR-044) rather than queueing behind it?

**Experiment.** Local harness: spawn the CLI with `--input-format stream-json --output-format stream-json
--verbose --session-id <uuid>`, start a long task, write a candidate user-turn frame to stdin mid-run, record
whether behaviour changes before the current request completes. Vary the frame shape until accepted.

**Exit criteria.** A documented frame shape, a documented delivery latency, and a documented answer on
in-flight versus queued. **If the format proves unstable, adopt the Agent SDK behind the same adapter boundary**
(R1) — the decision point, not a rewrite.

**Timebox.** Two days. This is the single highest-risk unknown in the feature.

### S2. Snapshot restore across instances (gates US3)

**Question.** Does a snapshot taken on instance A restore on instance B such that `--resume` finds the session
and the agent's filesystem beliefs match the restored tree?

**Experiment.** Run to a snapshot on one instance; restore onto a fresh one; resume; ask the agent what it
changed and why; verify uncommitted work is present. Include a deliberately truncated final line to exercise
FR-053.

**Exit criteria.** Restore-and-resume verified across instances, including the truncated-tail path.

**Timebox.** One day, immediately after S1 (it depends on the same harness).

### S3 — live-log transport under connection pooling (1 day)

**Question.** Does an SSE endpoint on the panel's runtime receive Postgres `LISTEN/NOTIFY` events through the
pooling mode the deployment actually uses, and does the stream reach the browser unbuffered through the CDN?

**Experiment.** Deploy the panel to a personal stage with the intended pooler configuration. Open a log stream
against a workflow emitting segments at ~10/second. Measure: notifications received vs emitted, end-to-end
latency at the browser, and behaviour at the runtime's duration limit with the stream still open.

**Exit criteria.** ≥95% of segments visible within 5 seconds (SC-002), no dropped notifications over a 10-minute
stream, and a defined behaviour when the runtime recycles mid-stream (client reconnects and resumes from its last
`sequence` without a gap).

**If it fails.** Adopt one of the two fallbacks in R6 — in-handler polling of `log_segments`, or an always-on
stream process. Both keep the SSE contract and the sequence-based reconciliation, so no other slice is affected.
This is the same shape as R1's fallback: a boundary chosen in advance so a failed spike is a swap, not a rewrite.
