# Impact of specs 003 and 004 on the spec 002 gap analysis

> **DEPRECATED (2026-08-11):** The Sisyphus workflow platform — including the executor, control plane, admin app, and agent credential pool described in this document — has been deprecated in favour of the Claude Code GitHub Action. This was because the GitHub Action is easier to maintain and configure, and more customizable than the bespoke infrastructure it replaced. This document is retained as a historical design record only; the packages and apps it describes have been removed from the repository.

Companion to [GAP-ANALYSIS-2026-08-09.md](./GAP-ANALYSIS-2026-08-09.md), which assessed spec 002's 34 open
tasks against the tree. This document asks the next question: **do the two later specs change what is
outstanding, and is any of it now superseded?**

**Method**: read-only throughout. Spec 004 was read from `feature/sisyphus-4`. Spec 003 was read from the
`feature/agent-credential-pool` branch ref and from the live files in that worktree, which is being worked by
another agent — nothing there was modified.

> **This is a snapshot of a moving target.** Spec 003 is mid-implementation: **53 of 129 tasks checked in the
> live worktree, 0 in the committed file**, so most of its progress is uncommitted and could change under this
> document. Every count and code reference below was taken on 2026-08-09. The structural conclusions —
> which requirements it supersedes — come from its own `Relationship to 002` table and are stable; the
> progress figures are not.

---

## 1. Answer in short

**Spec 004: no impact.** Already absorbed.

**Spec 003: real impact, and it is formally declared rather than implied.** It carries a `Supersedes:` header
and a `Relationship to 002` table. Of spec 002's 34 open tasks:

- **1 is absorbed** and should not be done standalone (T210)
- **2 have their scope materially grow** (T231, T222)
- **1 is upgraded from conditional to unconditional** (T197) — and this corrects the companion document
- **1 gains a new dependent** and moves onto 003's critical path too (T200)
- **2 have their test scripts made wrong** and need rewriting before they are run (T218, T219)
- **9 gain new prerequisites** (the assembly runs T213, T214, T220, T221, T223, T224, T225, T226, T140)
- **18 are unaffected**

**Nothing is cancelled.** Not one of the 34 becomes unnecessary. The changes are to sequencing, scope and
preconditions.

## 2. Spec 004 — settled, no action

`004-remove-reachability-gate` withdraws the repository-reachability half of the FR-124 profile-enable gate,
which was never implementable: the credential that could answer "is this repository readable?" exists only on
an ephemeral executor instance, installed by a client-authored bundle in a deliberately unspecified format.

**Status: 26 of 27 tasks done**, the single open item being a manual panel confirmation (its T014). The
removal is real in code — [profile-gate.ts:26](../../packages/sisyphus-api/src/server/admin/profile-gate.ts:26)
records the withdrawal, and spec 002's `tasks.md` already carries the amendment note on T079.

The companion analysis correctly did not list profile-enable as blocked. No revision needed.

## 3. Spec 003 — what it changes

`003-agent-credential-pool` replaces the assumption that the agent's credential is a static secret carried in
the setup bundle. It is false for a subscription login session, whose refresh credential rotates each time the
agent uses it: a bundle-carried copy is stale the moment the agent refreshes, and bundles are shared across
clients, so the value is both stale and shared. The credential becomes a pooled, leased entity.

Its declared supersessions ([spec.md:121](../003-agent-credential-pool/spec.md:121)):

| 002 requirement            | Was                                                       | Becomes                                                                                                  |
| -------------------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `002/FR-043`, `002/FR-075` | `setup.sh` installs the agent CLI **and its credentials** | Agent CLI and **non-agent** credentials only; the agent credential is leased                             |
| `002/FR-072`               | Credentials reinstalled from the bundle on every boot     | Agent credential fetched from its lease on every boot                                                    |
| `002/FR-049`               | Pause holds the agent process alive on a running instance | Pause **stops the instance** (on-demand); session persists on disk. Spot degrades to 002's snapshot path |
| `002/US2 §4`               | Paused too long → snapshot, release instance              | Unchanged, but the credential seat is **retained**                                                       |

It states explicitly what it leaves intact: access control, profiles, workspaces, integrations, supervision and
corrections, the strip-and-redact pipeline, notifications, snapshots as a durability mechanism, and the
reconciliation sweep.

### Where it has got to

| Phase                                                                               | Progress  |
| ----------------------------------------------------------------------------------- | --------- |
| 1 Setup                                                                             | 3/3       |
| 2 Foundational                                                                      | 15/15     |
| 3 US2 — credential groups scoped to profiles                                        | 9/9       |
| 4 US1a — register a credential                                                      | 8/8       |
| 5 US3 — a workflow leases a seat 🎯 MVP core                                        | **18/27** |
| 6–13 (waiting, hosted login, keep-alive, pause, park, pool admin, recovery, polish) | 0         |

Phases 1–4 are complete and Phase 5 is in flight. That is why this is not a hypothetical: the credential-group
gate is already live in that worktree.

## 4. Correction to the companion analysis

**T197 (`InstanceMetadataReader` against IMDS) was ranked A6 and qualified as "blocking only if
`purchase_mode` will ever be `spot`". That qualification was wrong. Spot is the default.**

Verified: [purchase-mode.ts:17](../../packages/sisyphus-api/src/enums/purchase-mode.ts:17) sets
`DEFAULT_PURCHASE_MODE: PurchaseMode = 'spot'`, and spec 003/FR-039 states it plainly — "spot is the platform
default". Spec 003 also keeps spot on the snapshot-and-terminate path rather than the new stop-the-instance
path, and its T127 asks for SC-007 to be recorded as two separate figures because the paths genuinely differ.

So spot is not an edge case to be decided later; it is what every run does unless someone overrides it. With
`watchForInterruption` running against `createQuietMetadataReader()`, **the default configuration silently
loses work on reclamation.** T197 belongs in the same tier as T231, not below it.

This does not change any other ranking in the companion document.

## 5. Impact on each open task

### Absorbed — do not do standalone

**T210** (the pause idle ceiling living in two files). Spec 003/FR-039 through FR-047 rewrite pause wholesale:
the instance is stopped rather than held alive, the seat is retained, and FR-044/FR-045 restate the park
behaviour with new conditions. Consolidating `PAUSE_IDLE_CEILING_MS` into `packages/sisyphus-api` is still
correct, but doing it before 003's pause work means touching the same constant twice. **Fold it into 003's
Phase 9/10 as an explicit sub-task** rather than leaving it on 002's list where it will be done at the wrong
time.

### Scope grows

**T231** (make the known-secret list a provider rather than a snapshot) — **more necessary, not less.** Spec
003 removes the agent credential from the bundle, but:

- non-agent credentials stay in the bundle (003/FR-048), so the original hole is untouched;
- a **new** credential arrives via the new `credential_install` bootstrap phase (003/FR-049), which
  [phases.ts](../../apps/sisyphus-executor/src/bootstrap/phases.ts) on that branch already schedules between
  `setup_script` and `entry_checkout`;
- 003/FR-050 makes that phase run on **every** boot, including restore and resumed-instance boots, because
  material may have rotated while the instance was stopped.

A rotating OAuth refresh token is exactly the value a pattern matcher will not recognise. The snapshot-at-step-1
design now fails to capture credentials arriving at _three_ different times. **Re-scope T231 to cover the leased
credential and implement it alongside 003's Phase 5, not before it** — otherwise it is written twice.

**T222** (Scenario 10, fleet oversight). Spec 003 adds a pool view (its Phase 11) and changes the spend story:
003/FR-042 requires a paused workflow to incur storage cost but not compute cost, **and for that to be
visible**. The fleet and spend screens gain a dimension.

### Gains a dependent

**T200** (validation runs cannot authenticate). Spec 003/FR-052: "Bundle validation runs MUST remain possible
without holding a credential, so proving a bundle does not consume pool capacity." That requirement **assumes
T200 is already solved** — a validation-mode executor still cannot reach the machine surface at all today.
T200 is now on both specs' critical paths, which is an argument for pulling it forward from where the companion
document placed it.

### Test scripts now wrong — rewrite before running

**T218** (Scenario 5, pause). The script as written checks that the agent "process [is] still alive" after a
pause. Under 003/FR-039 that is true only for spot; on-demand **stops the instance**. Running the current
script post-003 produces a false failure on the default path and a false pass on the other.

**T219** (Scenario 6, resume on a fresh instance). Snapshots stop being the _resume_ path for a pause and
remain the durability and recovery path. 003/FR-041 resumes by starting the existing stopped instance without
re-provisioning or restoring; 003/FR-043 adds a new case — a stopped instance that cannot be started must be
recovered from snapshot onto a fresh instance **holding the same credential**, with the substitution recorded.
That is a new scenario step, not a modified one.

### New prerequisite — a pool seat and a credential group

**T213, T214, T220, T221, T223, T224, T225, T226, and T140.** All nine end-to-end runs acquire a setup step
they do not currently describe.

The sharpest edge: spec 003/US2 acceptance 4 refuses a profile with no credential group attached as
unlaunchable, and this is **already implemented** on that branch —
`packages/sisyphus-api/src/server/admin/profiles.ts:237` calls `credentialGroupAttachmentCheck`. When 003
merges, **every execution profile in every deployment becomes unlaunchable until an administrator attaches a
credential group**, and the pool must hold at least one registered, logged-in seat.

This is the same class of event as spec 004's reachability gate — a configuration gate that refuses everything
until new setup exists — and it is worth being deliberate about it rather than discovering it on a stage.

### Unaffected (18)

T141, T142, T143, T196, T198, T201, T202, T203, T204, T205, T209, T211, T212, T215, T216, T217, T227, T228.

Three notes on that list:

- **T215–T217 and T227 become more valuable, not less.** Spec 003 is pushing ~129 tasks of new code through
  the same gates. A gate that measures nothing, and a suite that intermittently lies, cost more the more code
  passes through them.
- **T204** (panel query-state coverage for five panels) — 003's Phase 11 adds a pool view with the same
  convention. Fix the convention rather than the five instances, or the gap simply recurs.
- **T203** (wire `deploy.yml` to `getDeployRoleName`) and **T211** (stale comment in `scheduler.ts`) touch
  files 003 is actively changing — `sst.config.ts` across all three deployables, `packages/sisyphus-infra`
  (new `vpc.ts`, `panel-dns.ts`, `panel-domain.ts`, rewritten `policies.ts`), and the scheduler, which gains
  003's keep-alive schedule. Low severity, but expect merge conflicts; sequence them after 003 lands.

## 6. Two things neither spec's task list tracks

**The forge URL, again.** The companion document's A2 finding — `SISYPHUS_FORGE_API_URL` is required
non-optional by the executor's env schema and set by nothing in the repository — **is also true on the
credential-pool branch**. Confirmed: that branch has the schema, the env read and the tests, and still no
producer. Two branches, the same gap, still no task owning it. The credential-pool work is adding exactly the
kind of stage-configuration plumbing (`sst-env.d.ts`, expanded `env-schemas.ts`, `sst.config.ts`) where it
would naturally live, so this is a good moment to give it a home.

**The two specs contradict each other in the repository right now.** Spec 003's own **T126** — "Update
`specs/002-sisyphus-workflow-platform/` where this feature supersedes it — `002/FR-043`, `002/FR-049`,
`002/FR-072`, `002/FR-075` … so the two specs do not contradict each other in the repository" — is **open, and
sits in Phase 13 (Polish)**.

That is the wrong phase for it. Spec 002's `spec.md` and `quickstart.md` currently instruct a reader to build a
bundle that installs agent credentials and to expect a pause that holds the process alive. Anyone running a 002
scenario between now and 003's polish phase will be following superseded instructions. **T126 should move to
the front of 003's remaining work**, not the end — it is a documentation edit measured in an hour, and it is
the only thing standing between a reader and a wrong mental model of the platform.

## 7. Revised approach

The companion document's order assumed spec 002 was the only thing in flight. It is not. Revised:

### Stage 0 — unchanged, and now more urgent (days: ~1)

**T215, T216, T217, T227.** The three gate verifications and the flaky executor suite. Nothing else you learn —
about 002 or 003 — is trustworthy until the gates are proven against a planted failure and the test suite stops
being non-deterministic. Spec 003 is pushing a large volume of code through these same gates right now.

### Stage 1 — reconcile the documents before anyone reads them (hours)

**Pull 003's T126 out of Polish and do it.** Amend spec 002's `spec.md` and `quickstart.md` where FR-043,
FR-049, FR-072 and FR-075 are superseded. Also give **`SISYPHUS_FORGE_API_URL`** a task and a home, in the
credential-pool work where the stage-configuration plumbing is already being written.

### Stage 2 — prove the trunk _before_ 003 changes it (days: ~1, plus a stage)

**Run T213 (Scenario 2) now, against the current design.**

This is a change from the companion document's sequencing and it is deliberate. T213 is the only one of the
eleven assembly runs with no code blocker in front of it, and 003 is about to rewrite the credential path that
a delegated run depends on. If the first end-to-end run happens _after_ 003 lands and it fails, you will not
know whether the trunk was ever working or whether 003 broke it. Running it now converts an unknown into a
baseline, and it costs one stage and one afternoon.

Accept that the run will need the forge URL from Stage 1, and that the result will have to be re-run after
003 — a recorded pass now is still worth more than the ambiguity it removes.

### Stage 3 — the security work, sequenced with 003 rather than before it (days: ~2–3)

**T231, re-scoped.** Implement the secrets-provider change _alongside_ 003's Phase 5 credential-install work,
covering all three arrival times: envelope, bundle (phase 5), and lease (the new `credential_install` phase).
Doing it on 002's terms first means doing it twice.

**T197** at the same time, now unconditional. Spot is the default purchase mode; the interruption path is not
optional.

### Stage 4 — unblock the dead stories (days: ~3–5)

**T200** first — it is now on both specs' critical paths, and 003/FR-052 depends on it.
Then **T198** (package the prompt redactor; one package move plus a one-line override) and **T196** (the review
and autonomous ports). These are untouched by 003 and can proceed in parallel with the credential pool by a
different engineer — they share no files.

### Stage 5 — hold the remaining assembly runs until 003's Phase 5 lands

**T214, T218–T226 and T140.** Do not spend stages recording verdicts against a launch path that is weeks from
changing. Before running them:

1. Rewrite **T218** and **T219** for the new pause and resume semantics.
2. Add the pool prerequisite — a registered, logged-in seat and an attached credential group — to the setup
   step of every scenario.
3. Extend **T222** for the new pool view and the paused-storage-not-compute spend distinction.

**T222 still runs last**, for the reason it always did: oversight over an empty fleet proves nothing.

### Stage 6 — hygiene, after 003 merges

**T203** and **T211**, which touch files 003 is actively rewriting. **T204** fixed as a convention rather than
five instances. **T143** rescoped to its knip half, with T212's cspell findings spun out as a workspace-level
ticket. **T141**, **T142**, **T228**.
